# CAN 与 CPU 负载排查记录

日期：2026-10-08。目标板：HPM5361。本记录区分板上实测、代码结论与尚待复测的现象。最新一次 CPU 与 CAN 测试时电机已重新上电。

## 1. CAN 发送一段时间后停发

**已定位的故障在外部 HPM Zephyr CAN 驱动。** CAN 使用单次发送模式。一帧发送失败并被控制器取消后，现场寄存器为 `TXBRP=0、TXBTO=0、TXBCF=1`，但驱动中的 `tx_pending` 仍为真，发送完成回调没有执行。应用层随后无法正常提交下一帧。原先 Port 层的 5 ms 在途超时会反复停启 CAN 控制器；现场曾观察到每秒超过 100 次恢复，造成高 CPU 负载，并掩盖了真正的发送完成问题。

修复位于外部模块 `D:/MCU/hpm/zephyr_sdk_glue/drivers/can/mcan_hpmicro.c`：启用 TX 取消完成中断；在中断处理中遇到取消完成，或发现 `TXBCF=1` 且请求不再在途时，以错误结果结束当前发送并释放驱动状态。仓库保存了 [可重放补丁](../patches/hpm-mcan-tx-cancel.patch)，`CMakeLists.txt` 会在配置时检查该修复，避免换环境后静默构建出旧驱动。BSP 中没有 `mcan_hpmicro.c` 的副本。

电机上电、总线有负载时，修复后观察到 CAN0/CAN1 的发送完成和取消计数持续增长，`recovery_succeeded` 均保持为 0；运行数分钟没有重现原先的持续恢复。单次发送失败仍会发生，不同测试中 CAN0 发送错误占比约 15% 到 25%，CAN1 在拨弹禁用态保活降频前约 2% 到 12%；这些是总线发送结果，不能误认为驱动卡死已再次发生。控制帧采用最新值邮箱：同一目标的新控制值覆盖尚未发送的旧值；提交失败或完成失败的旧控制帧不会为了“可靠性”而延后重发。配置/使能类帧与周期控制帧分开处理。

外部 SDK 更新或重装后，需要在 `D:/MCU/hpm/zephyr_sdk_glue` 中应用 `patches/hpm-mcan-tx-cancel.patch`；未应用时构建配置会明确失败。保留 5 ms 在途超时仅作为驱动或硬件再次异常时的兜底诊断，正常运行不应靠它维持发送。

## 2. 调试时的异常崩溃

两次异常现场发现，ITCM 中地址 `0x2d0` 附近的 CAN 中断代码被写成相同的异常字节；复位刚进入 `main` 时，该处与 ELF 一致。这排除了“启动时未把代码复制进 ITCM”作为当前现场的解释。原 HPM OpenOCD 配置把工作区放在从 `0x0` 开始的 128 KiB ITCM，并设置 `backup=0`，与正在执行的中断代码重叠。异常现场分别出现过指令访问错误和加载错误；工作区覆盖与现场相符。

调试配置现将 OpenOCD 工作区移到空闲 AHB SRAM `0xf0406000`，大小 8 KiB；链接产物中的 AHB 数据段结束于 `0xf0404460`。采用该配置后曾连续运行超过 3 分钟并多次连接 GDB，ITCM 代码保持与 ELF 一致。但本次上电调试中，多次暂停/继续目标板后仍出现过加载异常：一次现场为 `mcause=5、mepc=0x2e0、mtval=0x02218c18`，CAN ISR 当时从无效的设备配置指针读取数据；本轮调试两次遇到同类 `mcause=5`，`mtval` 分别为 `0x02218c00` 和 `0x02218c44`，随后 CPU 停在 Zephyr fatal halt。断开 OpenOCD、复位后运行约 100 秒，再单次附加读取时未见停机，CAN 计数持续增长；但另一次 GDB 读取过程卡住并再次触发异常。这提示调试接入可能有关，但尚不能证明因果关系，也不能把所有崩溃归结为旧工作区覆盖。8 KiB 工作区不足以执行当前闪存算法，因此刷写任务仅在 `program ... verify reset exit` 期间临时使用原 128 KiB ITCM 工作区；**刷写时不要同时附加调试器或运行固件**。正常调试使用 `Board/hpm5361/hpm5361.cfg` 中的 AHB 工作区。

## 3. CPU 负载与收发路径

- `main` 中优先级为 0 的健康监测轮询间隔改为 10 ms，即 100 Hz。
- 接收回调按 CAN 外设和仲裁 ID 定位固定槽位，保存原始数据与时间戳；反馈解码在控制线程读取最新值时执行。收发没有依赖不断增长的消息队列。
- 周期控制帧按总线和 ID 合并，只保留待发送的最新值；Port 线程一次唤醒处理就绪总线，并通过 `ready_bus_mask` 跳过空闲总线。当前固定容量为 32 个电机绑定和 32 个控制槽位；未来设备超过容量时需要扩容，相关注册/提交接口会返回错误，不能假定无限容量。
- 当前 CAN2/CAN3 未接电机，升降控制不为它们生成电机命令；没有新反馈时，也不反复构造无法使用的 CubeMars 控制帧。
- CPU 使用率使用 Zephyr idle hook 统计。电机下电且 USB 转 CAN 拔出时曾测得约 17.6%；该值不能代表上电负载。2026-10-08 电机上电后，CAN0 约 4,000 帧/秒、CAN1 约 1,400 帧/秒，原固件平滑 CPU 使用率约 79%。CAN0/CAN1 恢复计数均为 0，说明此次红灯并非发送恢复循环直接造成。
- 线程运行统计的诊断固件显示 CAN Port、底盘和升降任务占用较多时间；中断时间可能计入被打断的线程，因此这些值不能直接当成各函数的独占耗时。底盘没有新运动指令时，原代码仍以 1 kHz 解码四路反馈并发送零电流帧。现改为无指令时每 20 ms 发送一次零电流帧，新指令到来或过期仍立即切换；1 kHz 活动控制保持不变。相同上电条件下，诊断构建约 61%，移除诊断统计后的最终构建两次测得约 57.2% 和 56.9%。
- 早期曾尝试将禁用状态的 DM 拨弹电机零扭矩帧降至 20 ms，但当时进入了 `motor_fault`，试验已撤回。不能把该试验期间约 54% 的 CPU 值作为有效优化结果。

本轮继续排查发现，上述 20 ms 试验的在线判断本身有问题：拨弹任务每 8 ms 只比较一次反馈计数，单个检查窗口没有新反馈就判离线，即使最新反馈时间戳仍在允许范围内，也会误判。现改为按反馈时间戳判断在线：启用控制时 12 ms，禁用时 30 ms；禁用且电机正常时每 5 ms 发送一次零扭矩保活，任务也切到 5 ms 节拍。启用入口立即唤醒任务并恢复 1 kHz；故障和运动状态也保持 1 kHz。无反馈时仍进入故障和原有恢复流程，不延后重发旧控制值。

发送路径另有两项开销缩减：`fdcan_port_init()` 在完成首次初始化后走原子快速路径，不再每次控制帧提交都进入初始化 mutex；逐帧创建/停止的 5 ms TX 看门狗改为在已有 1 kHz Port 节拍中检查在途超时，发送完成回调仍立即唤醒 Port，超时的旧周期帧仍被丢弃。刷入后、禁用拨弹且电机上电的本轮读数为：修改前约 69% 到 72%，只合并看门狗后约 69.0%，再调整拨弹零扭矩保活后约 61.6%，断开调试器复位运行约 100 秒后单次读取约 62.7%；最终把禁用态任务节拍也改为 5 ms 后，GDB 故障现场保留的最后 CPU 平滑值约 61.3%，故不能把这一读数当作无异常持续运行的验收值。CAN0 约 4,000 帧/秒、CAN1 约 900 到 1,300 帧/秒，CAN0/CAN1 恢复计数保持 0，两路 CubeMars 反馈新鲜，DM 状态保持 `disabled` 且反馈年龄约 2 到 4 ms。这组读数说明本轮修改降低了当前空闲控制工况负载，但不能外推到拨弹启用或底盘运动工况。

为核对高负载来源，随后临时启用 Zephyr tracing hook 和各工作段周期计数。电机上电、约 82 秒的诊断窗口中，CAN0/CAN1 合计约 5,170 帧/秒，ISR 累计时间约占窗口的 20.9%，升降任务工作段约 20.2%，CAN Port 工作段约 9.4%；IMU 工作段约 19.4%，其中姿态解算约 12.1%，SPI 读数区间约 7.2%。拨弹和底盘工作段分别约 2.7% 和 1.1%。CAN 接收 BSP 回调约 3.1%，包含在 ISR 中；反馈 Topic 读取约 6.2%，其中又包含 Port 反馈刷新。这些段之间有中断抢占、函数嵌套和 SPI 阻塞，**百分比不能相加，也不是各线程独占 CPU 时间**。另一轮电机下电、接收回调计数为 0 时，ISR 约 7.0%，升降约 2.7%，Port 约 0.8%。诊断构建本身的 tracing 开销较高，上电显示约 66%、下电约 30%，不能与正式构建的约 61% 和此前下电约 17.6% 直接对比。数据支持高负载由 CAN 中断、两路 1 kHz 升降控制及发送线程叠加造成；禁用态拨弹保活不是主因，也未观察到 CAN 恢复风暴。

升降两级 PID 当前均设置 `kd=0、kf=0`。通用 PID 原先仍为这两项每次计算除以 `dt`；现在零系数时跳过对应除法，保留积分和历史状态更新。该优化已通过编译和上电运行；优化后的正式固件在本轮 FIFO 修改前读到约 57.3% 和 58.5%。测试工况未严格锁定，不能把与此前约 61% 到 63% 的差值全部归因于 PID。上述临时 tracing 和计时点均已从正式源码移除。

电机下电时 CAN0 仍有约 50 帧/秒的底盘离线零输出，因没有对端应答，发送错误计数会增长；该现象不能当作电机上电后的丢帧率。

## 4. CAN1 CubeMars 离线判断

CAN0 与 CAN1 使用相同的 CubeMars 绑定、反馈刷新和超时判断流程，按 `(CAN 外设, 仲裁 ID)` 区分。用户已确认此前 CAN1 无反馈的原因是 **CAN 线松动**。重新接好并上电后，CAN0/CAN1 各一路 CubeMars 的反馈时间间隔实测约 1 到 2 ms，控制任务读取的反馈计数持续增长。此前板上 CAN1 接收槽也曾记录 `ID=0x000、DLC=6` 的报文，例如 `01 7D 8F 7F F8 02`。

当前不再把 CAN1 的历史无反馈当作软件离线检测差异。若后续再次出现“只发使能、不发控制”，先检查线束接触和对应反馈时间戳，再比较实际 TX ID 与使能应答。

## 5. Zephyr 中断与 MCAN 驱动核查

本轮电机上电时，先前正式固件的 CPU 平滑读数约 57.3% 和 58.5%；CAN0/CAN1 发送、接收计数持续增长，`recovery_succeeded` 和 `recovery_failed` 均为 0。正确的 MCAN0/MCAN1 基址分别是 `0xf0280000`、`0xf0284000`。两路现场 `ECR=0x110000`，即 TEC/REC 为 0、错误日志计数 CEL 为 17；`PSR` 分别为 `0x710`、`0x708`，BUS_OFF、ERROR_WARNING、ERROR_PASSIVE 位均未置位。一次早期调试读取误把 `0xf0290000` 当成 CAN1，那个地址的零值不能作为 CAN1 状态证据。

历史上电 tracing 窗口约 82 秒，全部 ISR 约 8,704 次/秒，CAN 接收回调约 5,170 次/秒、发送回调约 1,961 次/秒；另有系统时钟和其他外设中断。ISR 总数与实际事件量级相符，未观察到“没有新帧却不断重入”的中断风暴。ISR 累计耗时约占 20.9%，说明正常高帧率中断本身仍是重要负载。MCAN `IE=0x1ba80611` 包含新帧、发送完成/取消及错误事件，但不使能 FIFO 满/丢失事件；调试器暂停 MCU 后读到的 `IR` 中 FIFO 满/丢失位，不能反推正常运行时持续溢出。BSP 的 `rx_dropped` 也不是硬件 FIFO 丢帧计数。

对照 `C:/Users/63902/Desktop/hpm_support-main/drivers/can/mcan_hpmicro.c`，参考驱动和原驱动都在一次 RX FIFO 新帧中断中只读取一帧。若 ISR 进入时 FIFO 已积压多帧，最后几帧可能留到下一次新帧中断；在突发报文结束时尤其明显。现将本机外部驱动 `D:/MCU/hpm/zephyr_sdk_glue/drivers/can/mcan_hpmicro.c` 改为先读取 FIFO 填充量，再按该快照批量取帧，避免在持续输入下无界占用 ISR。中断标志继续在回调前清除，防止回调提交的新发送帧的完成标志被末尾清除。仓库补丁为 [RX FIFO 补丁](../patches/hpm-mcan-rx-fifo-drain.patch)，构建配置会检查两路 FIFO 处理均存在；原 [TX 取消补丁](../patches/hpm-mcan-tx-cancel.patch) 仍需保留。参考工程的 MCAN ISR 在末尾清标志，而且没有本项目所需的 TX 取消完成处理，不能直接替换。Zephyr `intc_plic.c` 的路径按 claim、设备 ISR、complete 顺序执行，板级 CAN0/CAN1 中断号为 35/36，未发现错误映射或漏 complete。

修复版已编译并刷入板上，OpenOCD 报 `Verified OK`。上电两次 CPU 平滑读数约 60.4% 和 54.7%；期间 CAN0 RX 从 182,498 增至 333,480、CAN1 RX 从 40,031 增至 59,161，TX 计数继续增长，两路恢复计数仍为 0，TEC/REC 仍为 0。CAN0 这段时间发送错误增加 7,088 次，提交增加 30,755 次，约占 23%；这是单次发送结果，仍需核查物理总线和仲裁条件。Port 的 `rx_dropped=286,761` 代表最新值槽被新反馈覆盖，符合“只关心最新帧”的策略，不能解释为硬件 FIFO 溢出。FIFO 修复主要解决积压时的正确性；当前 CPU 样本没有证明它能降低负载。

## 6. SPI 小包路径与进一步降负载

本板 CPU 时钟由 PLL0 960 MHz 除以 2，运行时 `hpm_core_clock=0x1c9c3800`，即 480 MHz；构建启用了速度优化和单精度 FPU，`CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC=24 MHz` 是系统计时器时钟，不能误认作 CPU 主频。用户提供的 168 MHz STM32F4 负载对比提示要继续查具体工作量；不同控制任务和访存条件下不能只按主频比例推算 CPU 使用率。

IMU 配置为 200 Hz，每次从状态寄存器到温度寄存器连续读取 26 字节。外部 HPM Zephyr SPI 驱动原把不超过 16 字节的收发走中断式 PIO，26 字节走双通道 DMA，需每次配置 DMA 和等待完成。将该驱动的 PIO 阈值调整到 32 字节后，同一笔 IMU 读取仍包含状态、加速度、角速度和温度，设备层解析与控制层接口均未改变。改动保存在 [SPI 小传输补丁](../patches/hpm-spi-small-transfer-pio.patch)，`CMakeLists.txt` 检查外部驱动已经应用。

同一上电工况下，调整前两次 CPU 平滑读数约 55.4%、55.2%；调整后连续三次约 51.4%、51.3%、51.3%。调整后 IMU 有效样本计数从 9,344 增至 20,376，按采样间隔仍约 200 Hz；样本内加速度、角速度、温度均非固定零值。CAN0/CAN1 收发计数持续增长，恢复计数与 ECR 的 TEC/REC 均为 0。CAN0 接收仍在约 5,000 帧/秒量级，CAN1 在约 200 帧/秒量级。这轮样本支持小传输走 PIO 可降低约 4 个百分点的 CPU 负载；仍需在动态升降、底盘运动和拨弹启用时检验时延和功能。

另做过仅将 MCAN 接收解析函数移入 ITCM 的对照：CPU 约 51.2%，与修改前约 51.3% 基本相同；已撤回该布局实验。多次 GDB 暂停/恢复后再次见到 `mcause=5` 加载异常，这次 `mepc=0x80008900` 位于 EKF 乘法代码、`mtval=0x02039c30`；已执行目标复位。异常与调试接入的关系仍未证明，不能因本次停机把 SPI PIO 路径判为错误，也不能忽略这项独立的稳定性问题。最终保留的固件为 SPI PIO 优化、MCAN FIFO 批量读取与 TX 取消处理，未包含 ITCM 布局实验。

## 7. 尚待验证

1. 当前 SPI 优化版在现有上电工况读到约 51.3%，仍需在底盘运动、升降目标变化及拨弹启用时复测 CPU 和控制时延。若要量化单项优化收益，需锁定相同电机反馈率与任务工况做前后对照。
2. 对调试时偶发的加载异常继续留存异常现场与是否连接调试器的条件；本轮再次出现同类故障，根因尚未确定。
3. CAN0 单次发送取消比例仍偏高。核对实际总线负载、波特率/采样点、线束/终端和其他节点错误计数；实时控制帧继续保持“过期即丢”，不重试旧目标值。CAN2/CAN3 当前无电机，不应按在线总线判断。
4. 若需继续明显降低上电 CPU，优先核对 HPM MCAN 每帧接收中断成本、升降控制线程的反馈读取与控制帧打包成本，以及 IMU 的姿态解算和 SPI 读数区间；不能仅凭最新值邮箱减少排队，就推断每帧 ISR 成本已经降低。若要证明正常运行时的硬件 FIFO 丢帧率，需要在驱动内单独计数 `RF0L/RF1L`，不能用调试暂停时的寄存器快照代替。

当前能确认的是：原发送卡住的驱动状态失配已修复，上电测试中 CAN0/CAN1 均没有反复停启；CAN1 历史无反馈由松动线束造成；没有观察到中断风暴。高负载是高频 CAN 收发、升降闭环和 IMU 等工作共同造成；MCAN FIFO 积压时只取一帧的问题已修复，SPI 26 字节小传输改走 PIO 后当前上电 CPU 约 51.3%。动态控制负载、硬件 FIFO 实际丢帧率及偶发调试异常仍需继续验证。

## 8. 遥控操作时负载升高

用户报告拨动遥控器后 CPU 负载进一步升高；目前尚无同一板上、相同电机状态的操作前后数值。代码路径可以确认：DT7 每收到一帧，`remote_channel_publish_sample()` 都会更新底盘指令时间戳，即使摇杆回中、速度目标为零也如此。底盘任务原先在无新指令时每 20 ms 发送一次零电流帧；有新指令后，每 1 ms 读取四路 C620 反馈、计算速度闭环并提交一帧 CAN0 控制报文。因此遥控器连接且持续上报时，就会触发底盘活动工况，CAN0 控制帧的理论提交频率由约 50 Hz 增至 1 kHz。该切换保留零速闭环制动，不能直接把回中指令当成离线并降频，否则会改变控制行为。

活动底盘原先每周期调用四次 `fdcan_topic_latest_feedback()`；每次分别进入 Port 的解码互斥锁、查找电机，并进入 Topic 的反馈锁查找。现新增按 `(总线, ID, 电机类型)` 的通用批量快照接口，底盘一次读取四路，Port 只进入一次解码互斥锁，Topic 只进入一次反馈锁。四路各自的时间戳、失联判断、PID 和 1 kHz 控制提交不变，其他单路调用方仍用原接口。新代码用项目交叉编译参数编译并完成链接，生成 ELF/HEX/BIN；本机 Ninja 执行阶段异常停滞，因此使用构建图中的原始命令逐步完成编译和链接。首次刷写遇到 JTAG 调试模块状态异常而失败；将适配器时钟从 100 kHz 降至 50 kHz 后，完整刷写、校验均成功，OpenOCD 报 `Verified OK` 并复位运行。

用户确认遥控器回中后，新固件运行约 183 秒的采样中，CPU 平滑值约 80.1%，遥控接收线程计数持续增长；一次 GDB `detach` 后曾把目标留在暂停态，随后明确 `resume` 并核对计数增长后才采用本读数。CAN0 累计提交 307,495 帧、完成 257,241 帧、发送错误 50,254 帧、接收 884,804 帧，折合约 1,680 次提交/秒及 4,827 帧接收/秒；CAN1 累计提交 185,153 帧、完成 184,532 帧、错误 621 帧、接收 184,532 帧，折合约 1,010 帧/秒。两路恢复成功/失败计数均为零。CAN0 控制报文频率和错误事件是高负载的重要线索，但此前约 51.3% 的样本中 CAN1 接收仅约 200 帧/秒，不能把两次读数的全部差额归因于遥控器或批量快照效果。尚缺少同一电机和总线条件下、遥控断开与回中以及拨动各轴的严格对照，也未实测动态控制时延。

下一步需要在安全的遥控回中状态刷入后记录三组可比样本：遥控断开或无新指令、遥控连接且回中、分别拨动左摇杆底盘轴和右摇杆升降轴。同步观察 CPU、CAN0/CAN1 收发和错误计数、反馈年龄及控制响应。若右摇杆单独操作也引起明显额外负载，而底盘帧率未变化，应重点核对动态反馈帧率和升降闭环饱和路径；现有静态证据不足以将全部增量归因于底盘任务。

## 9. 对照 wbr_control-main 的 CAN 架构

参考工程 `src/chassis_controller/communication/can_dispatch.cpp` 也使用最新值邮箱和固定槽位，待发槽位用短队列通知每路发送线程；接收回调按总线、ID 写入反馈邮箱。该项目在 **非 MCAN** 的 `can_hpmicro` 驱动上使用 `hpm_can_send_batch()`，先把至多三帧装入二级硬件 TX buffer，再一次触发和等待完成；相应实现位于 `hpm_support-main/drivers/can/can_hpmicro.c`。但是其 `CONFIG_MCAN_HPMICRO` 分支退回逐帧 `can_send()`，当前本板恰好使用该分支对应的 MCAN 硬件。当前外部 MCAN 驱动只开放一个 TX buffer，发送线程和队列本身不能产生硬件批量收益，还会增加调度对象。若要移植真正批量发送，需先扩展 MCAN 驱动的多 TX buffer、逐槽完成/取消及超时语义，不能仅复制参考工程的应用层代码；旧控制值仍必须过期即丢。

对照接收热路径，BSP 原先在 Zephyr 已给出的 `can_frame` 之外再清零和复制一个 64 字节数据区的 `fdcan_frame`，Port 最终只使用最多 8 字节。现改成回调期间有效的只读接收视图，由 Port 直接拷贝需要的 8 字节和时间戳；发送接口和电机协议层不变。该版本已交叉编译、完整链接并以 50 kHz JTAG 刷入，OpenOCD 报 `Verified OK`。回中运行约 58 秒时 CPU 平滑值约 80.08%，CAN0 提交 97,470 帧、接收 280,689 帧、发送错误 16,103 次，CAN1 提交 58,356 帧、接收 58,124 帧、错误 232 次；两路恢复计数仍为零。折合帧率和前一版回中样本接近，CPU 也与 80.14% 基本相同，说明省掉这次中间复制没有带来可测的整机 CPU 降幅。它保留为较短的接收数据路径，不能被当作高负载已解决的证据。
